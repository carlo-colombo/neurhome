# Neurhome Agent Notes

## Project Shape

- This is a single-module Android app: `app`; the package/namespace is `ovh.litapp.neurhome3`.
- `MainActivity` owns the Compose `NavHost`; UI screens and view models are under `app/src/main/java/ovh/litapp/neurhome3/ui`.
- `NeurhomeApplication` is the application-level composition root: it owns the Room database and constructs repositories/services. Data access is under `data`.
- The project uses Jetpack Compose, Material 3, MVVM, Kotlin coroutines/Flow, Room, KSP, and a Java 21 bytecode target (see the JVM policy below).
- Category UI is under `ui/categories`. The home destination uses `CategoryPager` with Home first, then tags, and Uncategorized last. The dedicated Categories destination uses the same tag/Uncategorized pages but starts directly with tags, without a Home dashboard page.
- Tag screens keep a centered title header fixed above independently vertically scrollable content. The full applications screen has a Categories action that opens the dedicated Categories destination; future tag screens must stay consistent between both category entry paths.
- Home already contains a horizontal calendar/weather pager. Do not assume an outer horizontal pager will receive gestures from its child; validate category gestures on a real device and preserve dashboard swiping.

## Architecture

- `NeurhomeRepository` is the read model over the app data and the facade the ViewModels inject. It delegates the per-concern reads and writes to five collaborators — `LauncherAppsSource`, `HomeRankingCoordinator`, `LaunchLogRepository`, `ApplicationMetadataRepository`, `DatabaseExporter` — which all share its single `CoroutineScope`. `close()` cancels that scope, and `NeurhomeApplication` closes the database only after it: the eager flows would otherwise keep a closed database alive. That ordering is load-bearing; do not reorder it.
- `NeurhomeApplication` keeps only process-wide services. Every singleton bound to the database file (the database, repository, settings/tag/favourites/calendar repositories, `ApplicationService`) is delegated to `DataLayerGraph`, which `rebindDataLayer` closes and rebuilds around the database-file swap. Do not cache those for the process lifetime: Room never reopens a closed instance.
- The debug logcat capture lives in the debug source set only: `DebugLogcatCaptureProvider` is declared in `src/debug/AndroidManifest.xml`, and the framework instantiates it at startup, so production code never references it. Do not move it behind `BuildConfig.DEBUG` in production.

## Build And Test

- Use the checked-in Gradle wrapper (`./gradlew`). Android SDK 37 is required to compile and the app minimum SDK is 34.
- **JVM policy — two distinct roles that are easy to confuse:**
  - The **app's bytecode target is Java 21** (`compileOptions.sourceCompatibility`/`targetCompatibility` and Kotlin `jvmTarget = JVM_21` in `app/build.gradle.kts`), matching the JVM that actually runs the build. Verified against AGP 9.4.1: it compiles, dexes and survives R8. If a future AGP upgrade rejects it, fall back to `VERSION_17`/`JVM_17` — 17 is the last level AGP documents as supported, so 21 here is deliberate, not implied by the toolchain.
  - The **Gradle daemon runs JetBrains Runtime 21**, pinned by `gradle/gradle-daemon-jvm.properties` (Gradle's `updateDaemonJvm` criteria). Gradle auto-provisions JBR 21 into `~/.gradle/jdks` when it is missing, so a local `JAVA_HOME` pointing at JDK 17 does **not** make the build run on 17, and CI must install the matching `jetbrains` distribution at version 21 or Gradle downloads a second JDK.
  - **Never shrink `org.gradle.jvmargs`.** The project sets `-Xmx4g -XX:MaxMetaspaceSize=1g`. Overriding it downwards (for example `-XX:MaxMetaspaceSize=512m`) makes D8 and the Kotlin compiler fail with `OutOfMemoryError: Metaspace` on the JDK 21 daemon. If a stale daemon holds memory or serves a stale classpath, run `./gradlew --stop` instead of lowering the heap.
- PR-equivalent build: `./gradlew :app:assembleDevDebug`.
- After every code change, build and deploy the dev debug APK to the attached device when available. Use `./gradlew :app:assembleDevDebug`, install `app/build/outputs/apk/dev/debug/app-dev-debug.apk`, resolve the current package from the build output or `adb shell pm list packages`, and launch `ovh.litapp.neurhome3.MainActivity`.
- Production build: `./gradlew assembleProdRelease`; release enables R8/resource shrinking and CI signs the resulting APK.
- JVM unit tests: `./gradlew :app:testDevDebugUnitTest`. The JVM stack includes Robolectric, `androidx.room:room-testing`, `kotlinx-coroutines-test` and Turbine, so the DAO and migration tests run on the JVM against real in-memory SQLite; only the Compose tests need a device.
- `app/src/test/resources/robolectric.properties` pins `sdk=37`, the API the app compiles against and targets, so the JVM suite covers API 35+ runtime behaviour (notably enforced edge-to-edge). Robolectric's API 37 `android-all` runtime is **declared and staged**, not fetched: `androidAllInstrumented` in the catalog names the artifact, the `copyRobolectricAndroidAll` task stages that jar into the build directory, and the unit-test tasks run with `robolectric.offline=true` against it. That removes a Maven fetch which used to happen while a test class initialised and 404'd intermittently in CI. The catalog version must be bumped in lockstep with the `sdk` pin - Robolectric 4.17 maps API 37 to android-all-instrumented `17-robolectric-15733970-i7` - or every Robolectric test fails with "Unable to locate dependency". Two API 37 specifics are load-bearing and documented here so a future sdk bump does not rediscover them: the API 36+ runtime initialises `ApplicationSharedMemory`, which reflects into `jdk.internal.access`, so the unit-test tasks pass `--add-opens=java.base/jdk.internal.access=ALL-UNNAMED` (without it every test fails in `AndroidTestEnvironment.setUpApplicationState`); and `LauncherActivityInfo.isVisible` now requires `Paint.hasGlyph`, which no Robolectric font stack can answer, so the globally registered `ShadowPaintHasGlyph` keeps launcher labels from silently degrading to the package name. Hidden-API signatures the tests reach reflectively can also move between API levels - API 37 added `LauncherActivityInfoInternal(ActivityInfo, IncrementalStatesInfo, UserHandle, boolean)` - so a `sdk` bump means re-running both unit-test variants, not just the dev one.
- Run `:app:testProdDebugUnitTest` as well as `:app:testDevDebugUnitTest` before pushing. The dev variant alone misses prod-flavour failures: a release run has already failed at the prod-variant validation step while the dev suite was green, which is why that step exists in `.github/workflows/build.yml`.
- Compose/instrumentation tests require a connected or running Android device/emulator: `./gradlew :app:connectedDevDebugAndroidTest`. A lane without a device cannot run them.
- Compose tests use the debug-only `ComposeTestActivity` when they need to call `setContent`; do not replace `MainActivity` content in tests because it initializes its own Compose hierarchy.

## Database

- The schema version is `NEURHOME_DATABASE_VERSION = 23` in `data/AppDatabase.kt`, and every hop from 1 to 23 is an `AutoMigration`. v21 dropped the unused `index_ApplicationLogEntry_packageName`, v22 added the covering `wifi` index for the SSID query, and v23 added the `ApplicationTag.tagName` index.
- `LogRetention` runs at most one pass a day on IO from `NeurhomeApplication`: it prunes launch-log rows older than `LOG_RETENTION_YEARS` (2), `VACUUM`s only when the freelist reaches `VACUUM_FREELIST_PERCENT` (25) of the pages, and runs `ANALYZE` once per app version code. `ANALYZE` is what lets the ranking queries seek the log index instead of scanning it, so do not remove it as noise.
- Room exports schemas to `app/schemas`. When changing entities or the database version, update the migration declarations and commit the generated schema output; do not delete historical schema versions. CI fails a build whose schema export is not committed.
- Room uses KSP during the Gradle build; generated output belongs in build directories, not source control.

## Flavors And Generated Files

- `dev` adds `.dev.<hostname>` to the application ID and `-dev-<hostname>` to the version name, so dev APK identity varies by machine; `prod` has no suffix. Both suffixes come from the `devHostSuffix` Gradle property; it defaults to the local short hostname, and CI passes `-PdevHostSuffix=ci` so the dev variant — and with it the remote build cache entries keyed on the variant's outputs — is identical across machines instead of differing per builder. Override it locally the same way when a stable dev identity is wanted.
- For manual dev deployment, install `app/build/outputs/apk/dev/debug/app-dev-debug.apk`, then resolve the package from the current build output or `adb shell pm list packages`; launch `ovh.litapp.neurhome3.MainActivity` using that package. Do not hard-code another machine's hostname suffix.
- Keep application initialization blocks after the properties they access. In particular, `NeurhomeApplication` must initialize repository lazy properties before starting collectors that reference them.

## CI And Releases

- Trunk-based: every push to `main` publishes a signed release tagged `<version>-build.N`. `PRERELEASE: true` in `build.yml` only shapes that tag name; it does not mark the GitHub release a prerelease, and publishing every push as "Latest" is intended.
- The release workflow validates the prod variant before signing — `:app:testProdDebugUnitTest` and `:app:lintProdRelease` (AGP 9 creates no `testProdReleaseUnitTest` task) — then resolves the highest installed build-tools version that ships `apksigner` and signs with explicit `zipalign`/`apksigner` steps instead of a third-party action.
- Branch protection is deliberately NOT configured and PRs are mostly dependabot, so the always-on `required-checks` job is a signal only. Do not describe it as a gate.
- PR CI builds the dev debug APK and runs `:app:assembleDevDebug :app:testDevDebugUnitTest :app:lintDevDebug` in one `--parallel` invocation with `-PdevHostSuffix=ci`, verifies the Room schema export is committed, and runs the (non-blocking) instrumented suite on an API 34 emulator plus `tools/tests` under pytest.

## Backup Policy

- A custom backup agent owns the database. `android:backupAgent=".backup.NeurhomeBackupAgent"` is declared in `AndroidManifest.xml`. `NeurhomeBackupAgent` calls `super.onFullBackup` so every non-database domain keeps the rule-XML scheme, then appends the Room database `neurhome_database` as a gzip-compressed payload via `fullBackupFile`. The raw database outgrew the 25 MB Auto Backup cloud quota (it was being skipped silently), so the agent compresses it to `neurhome_database.backup.gz` **next to the database in `databases/`, not in the cache directory**: `BackupAgent.fullBackupFile` silently ignores cache, code-cache, no-backup, and native-library files. It runs `PRAGMA wal_checkpoint(TRUNCATE)` first so the copy is complete, and `onRestoreFile` decompresses the payload back over `neurhome_database`, dropping stale `-wal`/`-shm`/`-journal` sidecars. See `app/src/main/java/ovh/litapp/neurhome3/backup/`.
- The database domain is deliberately absent from the `<cloud-backup>` include list in `data_extraction_rules.xml` (and `backup_rules.xml`), so the framework's own cloud pass never uploads the raw file; the agent's compressed payload is the only cloud copy. It is omitted, not `<exclude>`d: a section with any `<include>` is narrowed to exactly the listed paths, and Android Lint's FATAL `FullBackupContent` check rejects an exclude whose domain has no matching include. `<device-transfer>` still includes the database, so device-to-device transfer carries the raw file through the framework and the agent adds nothing there (`shouldUploadDatabasePayload` returns false when `FLAG_DEVICE_TO_DEVICE_TRANSFER` is set). Including the database (and therefore the `ApplicationLogEntry` launch log: package name, timestamp, Wi-Fi SSID and state, latitude, longitude, geohash, user, query text) in backup and device transfer remains a deliberate product decision; only the cloud path goes through the agent.
- Cloud backup REQUIRES client-side encryption: every `<cloud-backup>` `<include>` in `data_extraction_rules.xml` and every `<include>` in `backup_rules.xml` carries `requireFlags="clientSideEncryption"`. The agent re-enforces client-side encryption **in code** for the database payload, because overriding `onFullBackup` means that XML attribute no longer governs the file the agent writes: `shouldUploadDatabasePayload` reads `FullBackupDataOutput.getTransportFlags()` and adds the payload only when `FLAG_CLIENT_SIDE_ENCRYPTION_ENABLED` is set. On a device without a secure lock screen every cloud include is ineligible and the transport lacks the CSE flag, so cloud backup uploads nothing at all, while device transfer still carries the full database. That tradeoff is accepted: the launch log is sensitive enough that not backing it up is preferred over uploading it unencrypted. The `<device-transfer>` includes deliberately do not carry the flag, because client-side encryption is a cloud-backup concept and local transfer must keep working without a lock screen.
- `disableIfNoEncryptionCapabilities="true"` is intentionally not set on `<cloud-backup>`: with every include already flagged, an unencrypted device has nothing the framework may upload, so the attribute would only restate the same outcome.
- `app/src/test/java/ovh/litapp/neurhome3/BackupRulesTest.kt` pins the rule shape: the cloud-backup section must carry no database include, `<device-transfer>` must still include it, every cloud-backup include must keep `requireFlags="clientSideEncryption"`, and no device-transfer include may gain it. `app/src/test/java/ovh/litapp/neurhome3/backup/DatabaseBackupPayloadTest.kt` pins the agent's transport-flag decision and a real gzip round-trip. Changing the rules or the agent without updating these fails `:app:testDevDebugUnitTest`.

## Development Learnings

- Key application `LazyColumn` rows with package, profile, and launcher component. Package/profile alone is not unique when an application exposes multiple launcher activities.
- After a successful dev build, deploy `app/build/outputs/apk/dev/debug/app-dev-debug.apk` to the attached device and launch the package resolved from `output-metadata.json`.
- Category screens should collect a remembered flow; creating a new flow during recomposition can reset collection to its empty initial state and cause visible flicker.
- Category data should use a shared launcher-app flow joined with tag assignments, rather than waiting for unrelated usage statistics or contacts flows.
- The Uncategorized screen uses a compact add-tag row without a separate screen header; preserve its test tags when changing the controls.
- Uncategorized is the final page in category pagers. Pager tests must swipe through remaining tag pages and wait for pager settling before asserting that page, rather than assuming one swipe reaches it.
- Tag ordering is persisted as contiguous `Tag.position` values and must be queried with `ORDER BY position, name COLLATE NOCASE`; reorder, create, and delete operations should preserve valid positions.
- The tag reorder controls are rendered by the shared `CategoryPager`, so changes must preserve behavior in both the Home pager and the dedicated Categories destination.
- Room schema changes require committing the newly exported schema JSON; adding a non-null field also requires a `@ColumnInfo(defaultValue = ...)` so Room can generate the auto-migration.
- For manual APK smoke checks, `apkanalyzer` may not be installed. Resolve the dev application ID with `adb shell pm list packages --user 0` after installation, then launch `ovh.litapp.neurhome3.MainActivity` through the resolved package.
- Application detail is an expanded `ApplicationItem` row: keep the initial tag set separate from the edited set, and persist the final selection only when the row collapses. Use the stable row key for remembered state so category flows remain unchanged during editing.
- Replace an application's tag assignments with a delete-all-then-insert operation inside a Room transaction; this handles zero, one, and multiple tags consistently and avoids incremental category updates while editing.
- The Home-ranking chronological parity test (`PairwiseHomeAppChronologicalParityTest`) is fixture-gated: it runs only when `HOME_APP_RERANKER_PARITY_FIXTURE` points at the anonymized export from `tools/evaluate_home_app_reranker.py --kotlin-parity-fixture`, and is skipped otherwise. Never commit the fixture or the personal database; the export must stay identifier-free (integer label IDs, hashed features only).
- `SettingsRepository` takes an optional coroutine scope that defaults to `Dispatchers.IO` (it used to be `Dispatchers.Main` with each write dispatched to IO). Pass `CoroutineScope(Dispatchers.Unconfined)` in JVM unit tests so writes land synchronously.
- The `home.app.selection` preference is stored independently of its prerequisites, and an unknown stored value parses back to `CLASSIC`. Requirement checks live in `ui/settings/LearnedRankingPrerequisites.kt`; the Settings row is the stateless `HomeAppSelectionSelector`, which is what Compose tests drive so they never need real permissions.
- Contact rows carry their thumbnail `content://` URI in `Application.photoUri` and leave `Application.icon` null; the UI decodes a photo only for a row it composes, through `rememberContactPhoto` and the process-wide `ContactPhotos` LRU owned by `NeurhomeApplication`. Never decode thumbnails inside a contact list read: with `ContactCandidates.ALL` that would be thousands of decodes per refresh. Launcher rows keep carrying a `Drawable` in `Application.icon`, and both call sites (the row icon and the favourites bar) go through `ApplicationIcon`.
- The contact scope is one tri-state setting, not two flags: `ContactCandidates.NONE | STARRED | ALL` stored as `contacts.call.candidates`. `show.contacts.starred` is still read as a fallback (an upgrading install keeps its starred contacts) but is never written again. The list re-reads on the same 5-minute tick for every scope (a scope change re-reads immediately), which is affordable only because photos are lazy: a full address book read is a cursor scan, not a decode pass.
- Contact rows are one per phone number, keyed by the call URI (`distinctBy { packageName }`), not one per display name: a label is not an identity, and the call URI is what the launch log and the ranking resolve against.
- T9 keyboard keys are Material 3 `Button`-based `Keycap`s, so they already have `Role.Button`; their accessible name must add the digit (`"3, d, e, f"`), set via `Modifier.semantics { contentDescription = ...; onClick(label = ..., action = null) }`, with the inner glyph wrapped in `clearAndSetSemantics {}` so the visible label is not announced twice. The query row is a polite live region with a readable (`[abc]` → `abc`) description.
- `MainActivity`'s root `Box` sets `Modifier.semantics { testTagsAsResourceId = true }`, which exposes Compose `testTag`s as UiAutomator/Appium/Maestro `resource-id`s (e.g. `keyboard`, `keyboard-key-def`). Keep those tag constants stable when renaming UI.
- Connected Compose tests require the device screen to be awake: a sleeping/locked device makes every `createAndroidComposeRule` test fail with `No compose hierarchies found in the app`. Run `adb shell svc power stayon true` and wake the device before `:app:connectedDevDebugAndroidTest`.
